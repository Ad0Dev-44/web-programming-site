Regular Expressions in Forms

A regular expression (regex) is a pattern used to match text. In HTML forms, the pattern attribute lets a text input reject any value that does not match a given regex, without writing any JavaScript. The browser checks the pattern automatically when the form is submitted.

The pattern Attribute

The pattern attribute accepts a JavaScript-style regular expression (without the surrounding slashes). If the input's value does not fully match the pattern, the browser blocks submission and shows a validation message, which can be customized with the title attribute.

Example — a text field that only accepts a 5-digit ZIP code: 

                <input type="text" 
                          name="zip" 
                          pattern="^\d{5}$" 
                          title="Enter a 5-digit ZIP code"
                          required>

Source: MDN — pattern attribute

Common Validation Patterns

A few patterns come up constantly in real forms. They are a starting point, not a guarantee — regex validation on the client is about catching honest typos early, not security.

Field Pattern Matches
Email (simple) ^[^\s@]+@[^\s@]+\.[^\s@]+$ text@text.text with no spaces
US ZIP code ^\d{5}$ Exactly 5 digits
US phone number ^\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}$ (123) 456-7890, 123-456-7890, 1234567890
Username ^[A-Za-z0-9_]{3,16}$ 3–16 letters, numbers, or underscores
Password (letter + number, 8+ chars) ^(?=.*[A-Za-z])(?=.*\d)[A-Za-z\d]{8,}$ At least one letter, one digit, 8+ characters

Source: MDN — Regular Expressions Guide

Client-Side Validation Is Not Security

The pattern attribute runs entirely in the browser, so it improves user experience by catching mistakes immediately — but it can be bypassed by disabling JavaScript, editing the HTML, or sending a request directly to the server. Any value that matters (an email that must be unique, a price, a permission level) has to be validated again on the server, in Flask's case with something like request.form checks or a library such as WTForms.

Source: MDN — Client-Side Form Validation

Button vs. Input Button

HTML gives you two different ways to make a clickable button in a form, and they behave differently in a way that regularly trips people up: <button> and <input type="button"> (or type="submit" / type="reset").

Default Behavior Inside a Form

The biggest gotcha: a plain <button> with no type attribute defaults to type="submit" when placed inside a <form>. That means it will submit the form even if the intent was just a decorative or JavaScript button, unless type="button" is set explicitly. An <input type="button">, by contrast, never submits a form on its own — it does nothing until a script is attached to it.

Source: MDN — <button> element

Content Model

<input> is a void element — it can never have child elements, so its visible label comes only from its value attribute and is always plain text. <button> is a container element, so it can hold an icon, an image, or styled <span> text inside it, which makes it far more flexible for design. 

<!-- input: label must be plain text -->
<input type="submit" value="Send Message">

<!-- button: can contain markup -->
<button type="submit">
    <img src="send-icon.svg" alt=""> Send Message
</button>

Comparison Table

Element Default Type Can Contain HTML? Typical Use
<button> submit (inside a form) Yes Submit buttons with icons/labels, or JS-only buttons with type="button"
<input type="button"> None — does nothing by itself No (text only, via value) Simple JavaScript-triggered actions
<input type="submit"> submit No Simple text-only submit buttons
<input type="reset"> reset No Clearing all fields in a form

Source: MDN — <input type="button">

CSS At-Rules

At-rules are CSS statements that start with @ and instruct the stylesheet to do something conditional or structural, rather than just style an element directly. The most common one in responsive design is @media, but several others show up often enough to be worth knowing.

@media — Responsive Breakpoints

@media applies a block of CSS only when a condition is true — most often the width of the viewport. This is the core tool behind responsive, mobile-friendly layouts. 

/* Stack a two-column layout on narrow screens */
@media screen and (max-width: 600px) {
    .content-columns {
        flex-direction: column;
    }
}

Source: MDN — @media

@import — Pulling In Other Stylesheets

@import loads another CSS file's rules into the current stylesheet. It must appear before any other rules (other than @charset), and each imported file triggers an extra network request, so it's generally slower than linking stylesheets directly in the HTML <head>. 

@import url("reset.css");

Source: MDN — @import

@font-face — Custom Fonts

@font-face lets a page load and use a specific font file instead of relying only on fonts already installed on the visitor's device. 

@font-face {
    font-family: "MyHeadingFont";
    src: url("fonts/myheadingfont.woff2") format("woff2");
}

Source: MDN — @font-face

@keyframes — Animation Sequences

@keyframes defines the stages of a CSS animation, which an element then plays using the animation property. 

@keyframes fade-in {
    from { opacity: 0; }
    to   { opacity: 1; }
}

.card {
    animation: fade-in 0.4s ease-in;
}

Source: MDN — @keyframes

@supports — Feature Queries

@supports applies a block of CSS only if the browser actually supports a given property or value, allowing a fallback style for older browsers. 

@supports (display: grid) {
    .layout {
        display: grid;
        grid-template-columns: 1fr 1fr;
    }
}

Source: MDN — @supports
